I've been extending that into AWS infrastructure and DevOps. This post is the hands-on walkthrough from that work: going from "no AWS account" to "a VPC created by Terraform". Along the way I ran into a handful of common snags, and I've included each one with its fix so you can skip the detours. Follow along step by step.

> **Note on sensitive values:** every account ID, email address, username and key in this post is a placeholder (`<YOUR_ACCOUNT_ID>`, `<your-admin-user>`, and so on). Never publish your real ones.

## What we'll build

By the end you will have:

1. A secured AWS account (root user locked down, billing alert set)
2. An IAM admin user in a group, instead of using root
3. The AWS CLI logged in with short-term credentials (no long-lived access keys)
4. Terraform installed
5. A small VPC (one public subnet, one private subnet) created, inspected and destroyed with Terraform

**Cost:** everything in this post is free. A VPC, subnets, route tables and an internet gateway don't cost anything. The one thing that does cost money in VPC land is a **NAT Gateway** (roughly $32/month at the time of writing, billed hourly whether you use it or not), so we deliberately don't create one. Check the current [NAT gateway pricing](https://docs.aws.amazon.com/vpc/latest/userguide//nat-gateway-pricing.html) before creating billable resources, because prices vary by region and change over time.

## Prerequisites

- A credit card (AWS requires one to sign up)
- A Windows machine. This guide is Windows-only, and every command is run in PowerShell.
- About 60-90 minutes

## Part 1: Create and secure the AWS account

### 1.1 Sign up

Go to aws.amazon.com and create an account. The email and password you sign up with create the **root user**, the most powerful identity in your account. It can close the account and change billing, and it can't be restricted. We'll set it up carefully and then basically never use it.

> **Analogy:** the root user is the **master key to an entire office building**. It opens every door, including the ones to the finance office and the building's deeds. You'd keep it locked in a safe and hand out ordinary staff keycards for day-to-day work. That's exactly what IAM users are for, which we set up in Part 2.

### 1.2 Turn on MFA for the root user

Sign in as root, open the **IAM** service, and go to **My security credentials**. Add a multi-factor authentication (MFA) device (an authenticator app is fine). AWS's own guidance on protecting this account is in [Root user best practices for your AWS account](https://docs.aws.amazon.com/IAM/latest/UserGuide/root-user-best-practices.html).

### 1.3 Set a billing alert before building anything

Go to **Billing > Budgets > Create budget**. A monthly cost budget of around $30-40 with an email alert at 80% is a good safety net while learning. Doing this first means a forgotten resource can't quietly run up a surprise bill. See [Managing your costs with AWS Budgets](https://docs.aws.amazon.com/cost-management/latest/userguide/budgets-managing-costs.html) and [Creating a cost budget](https://docs.aws.amazon.com/cost-management/latest/userguide/create-cost-budget.html).

## Part 2: Create an IAM admin user (stop using root)

From now on, everything you do should be as an IAM user, not root.

Go to **IAM > Users > Create user**. The wizard has several screens, and a few of them are worth a closer look.

### 2.1 "Provide user access to the AWS Management Console"

This checkbox controls whether the user can log in through the browser with a username and password. Unchecked, the user can only be used programmatically.

**Tick it.** You'll want to click around IAM, Billing and later other services to see what Terraform created. Then:

- Choose **autogenerated password** and save it in a password manager
- Leave **"User must create a new password at next sign-in"** ticked

### 2.2 "Set permissions"

AWS offers three routes: add the user to a group, copy permissions from another user, or attach policies directly.

**Use a group.** Permissions attached to a group apply to everyone in it, so a second user later doesn't mean re-attaching policies by hand and risking drift.

1. Choose **Add user to group**
2. Click **Create group**
3. Name it `Administrators`
4. Attach the AWS-managed policy **`AdministratorAccess`**
5. Add your user to that group

> **Analogy:** a group is a **job role on a staff badge**. You don't program each person's keycard door by door. You define what an "Administrator" badge opens once, then give the badge to whoever holds that role. Change the role and everyone holding it changes with it. Without groups, you'd re-edit every individual keycard each time the rules changed, and they'd slowly drift out of sync.

`AdministratorAccess` is fine for a solo learning account. In a real company, standing full admin access for a human is something a security review will want scoped down. Further reading: [IAM user groups](https://docs.aws.amazon.com/IAM/latest/UserGuide/id_groups.html) and [Security best practices in IAM](https://docs.aws.amazon.com/IAM/latest/UserGuide/best-practices.html).

### 2.3 "Set permissions boundary" (optional)

A permissions boundary puts a ceiling on what a user can ever be granted. It's meant for delegating IAM management to people you don't fully trust to hand out permissions safely. On a solo account you'd only be capping your own access, so **skip it**.

> **Analogy:** a new manager is allowed to issue keycards to their team, but company policy says *no card they create can ever open the server room*, no matter what they try to grant. The boundary is that company-wide ceiling. It only matters when you've delegated card-issuing to someone else.

Docs: [Permissions boundaries for IAM entities](https://docs.aws.amazon.com/en_us/IAM/latest/UserGuide/access_policies_boundaries.html).

### 2.4 Tags (optional)

Tags are key-value labels for organising resources. They're optional here. If you want them, `Project = my-learning-project` is plenty.

### 2.5 Sign in as the IAM user

IAM users don't sign in on the generic root login page. Use the account-specific URL:

```
https://<YOUR_ACCOUNT_ID>.signin.aws.amazon.com/console
```

Your 12-digit account ID is shown in the top-right menu of the console. Enter the account ID, your IAM username and your password.

## Part 3: Set up the AWS CLI with `aws login`

### 3.1 Why I didn't create an access key

When I got to **Security credentials > Create access key**, the console showed this message:

> **Alternatives recommended**
> - Use AWS CLI V2 and the `aws login` command to use your existing console credentials in the CLI.
> - Use AWS CloudShell, a browser-based CLI, to run commands

Access keys are long-lived credentials. If one leaks (for example, committed to GitHub), it stays valid until you revoke it. `aws login` instead gives your CLI **short-term credentials** that expire on their own, based on your console login. CloudShell is handy for quick tasks but a poor fit for Terraform, because your `.tf` files live on your own machine.

So I went with `aws login`.

> **Analogy:** an access key is a **permanent copy of your house key**. If you drop it, whoever finds it can walk in until you change the locks. `aws login` is a **hotel keycard** that stops working after a set time, so a lost one is far less dangerous. CloudShell is like using the hotel's own front-desk computer: convenient, but your files aren't there.

Docs: [Login for AWS local development using console credentials](https://docs.aws.amazon.com/cli/latest/userguide/cli-configure-sign-in.html), [Sign in through the AWS Command Line Interface](https://docs.aws.amazon.com/signin/latest/userguide/command-line-sign-in.html), and the [AWS announcement](https://aws.amazon.com/about-aws/whats-new/2025/11/console-credentials-aws-cli-sdk-authentication/) of the feature.

### 3.2 Check your CLI version (pitfall #1)

```powershell
aws --version
```

`aws login` needs **AWS CLI v2.32.0 or higher** (confirmed in the [AWS CLI user guide](https://docs.aws.amazon.com/cli/latest/userguide/cli-configure-sign-in.html)). I had `aws-cli/2.31.14`, which is just below that. The official upgrade steps are in [Installing or updating to the latest version of the AWS CLI](https://docs.aws.amazon.com/cli/latest/userguide/getting-started-install.html). Upgrade it:

Download and run the latest 64-bit MSI installer from the AWS CLI install page. It upgrades your existing install in place, so there's no need to uninstall first.

Open a **new** terminal and confirm `aws --version` now reports 2.32.0 or later.

### 3.3 Run `aws login` (pitfall #2)

```powershell
aws login
```

For me this stopped with:

```
Profile 'default' is already configured with Access Key credentials.
```

That's a safety check, not a bug. I had run `aws configure` earlier, so the CLI found static keys in my `default` profile and refused to silently replace them with a different credential type.

**Fix (option A):** back up the old credentials file, then log in again.

```powershell
Rename-Item $env:USERPROFILE\.aws\credentials credentials.backup
aws login
```

**Fix (option B):** keep the old keys and log in under a separate profile instead:
```powershell
aws login --profile <your-profile-name>
$env:AWS_PROFILE = "<your-profile-name>"
```

### 3.4 What region should I enter?

The CLI asks for a default region. Pick the one closest to you, since that gives the lowest latency. I used **`eu-west-2`** (London). IAM itself is a **global** service, so it doesn't matter which region you were looking at when you created your IAM user.

### 3.5 Log in as the admin user, not root (pitfall #3)

When the browser opens during `aws login`, sign in as your **IAM admin user** from Part 2, not as root.

My first attempts failed with:

```
Authentication failed
Your authentication information is incorrect. Please try again.
```

That's the generic console sign-in error. The most common cause is using the wrong sign-in page: the default page expects the **root user's email**, so typing an IAM username there fails. Go to the account-specific sign-in URL from step 2.5 and enter the account ID, IAM username and password separately. If you're certain they're right, reset the IAM user's password from the root account (**IAM > Users > your user > Security credentials > Console sign-in**), and watch for similar-looking characters (`0`/`O`, `1`/`l`/`I`) and trailing spaces when pasting.

### 3.6 Verify

```powershell
aws sts get-caller-identity
```

You should see your account ID and the ARN of your **IAM user** (not root). Example with masked values:

```json
{
    "UserId": "AIDAXXXXXXXXXXXXXXXXX",
    "Account": "<YOUR_ACCOUNT_ID>",
    "Arn": "arn:aws:iam::<YOUR_ACCOUNT_ID>:user/<your-admin-user>"
}
```

If the ARN ends in `:root`, you've logged in as root and should redo the login with the IAM user.

## Part 4: Install Terraform

### 4.1 The error (pitfall #4)

```
'terraform' is not recognized as an internal or external command
```

That means Windows can't find `terraform` on your **PATH**: either it isn't installed, or the folder holding `terraform.exe` isn't on the PATH. It has nothing to do with AWS.

> **Analogy:** PATH is your **phone's contacts list**. When you type a command, Windows only "calls" programs listed in its contacts (the folders on PATH). Installing Terraform puts the program on your phone, but until you add its folder to the contacts list, typing its name reaches nobody.

HashiCorp's own walkthrough is [Install Terraform](https://developer.hashicorp.com/terraform/tutorials/aws-get-started/install-cli), and the download page is [developer.hashicorp.com/terraform/install](https://developer.hashicorp.com/terraform/install).

### 4.2 Fix: install it properly

The quick way on Windows:

```powershell
winget install HashiCorp.Terraform
```

Or with Chocolatey: `choco install terraform`.

The manual way:

1. Download the Windows AMD64 zip from the Terraform install page
2. Extract it to a permanent folder such as `C:\terraform` (so you have `C:\terraform\terraform.exe`)
3. Search Windows for "Environment Variables" > **Edit the system environment variables** > **Environment Variables** > under *System variables* select `Path` > **Edit** > **New** > add `C:\terraform`
4. **Close your terminal completely and open a new one.** PATH changes only apply to new terminals, and skipping this step is the classic reason people think it didn't work.

Verify:

```powershell
terraform version
```

`where terraform` shows which copy is being picked up.

## Part 5: Your first Terraform project, a VPC

### 5.1 The vocabulary

| Keyword | What it means |
|---|---|
| `provider` | A plugin that knows how to talk to a cloud (here, AWS) |
| `resource` | Something Terraform creates (a VPC, a subnet) |
| `variable` | An input to your code, like a function parameter |
| `output` | A value Terraform prints after it finishes |
| `module` | A reusable folder of Terraform code (not used in this post) |
| **state** | Terraform's memory of what it has already created |

### 5.2 A quick networking primer

Picture **an office campus**, and keep it in mind through the whole post:

| AWS thing | The office-campus analogy |
|---|---|
| **VPC** | The fenced campus itself, a private area that belongs only to you |
| **Availability Zone** | A separate building on a different street, so a power cut at one doesn't affect the other |
| **Subnet** | A wing or floor inside one building |
| **Internet Gateway** | The front door to the public street |
| **Route table** | The signs and directory in the corridors, which say "to reach the street, go this way" |
| **Public subnet** | The reception and meeting area, facing the street with visitors allowed |
| **Private subnet** | The back-office or server room, with no door to the street |
| **NAT Gateway** | A receptionist who makes phone calls out for the back office without revealing their direct numbers, so people outside can't call them back |

For the official explanation of how these pieces fit together, read [How Amazon VPC works](https://docs.aws.amazon.com/vpc/latest/userguide/VPC_Subnets.html).

The details:

- **VPC**: your own private network inside AWS
- **Subnet**: a slice of the VPC that lives in one Availability Zone (a physically separate data centre)
- **Public subnet**: has a route to an Internet Gateway, so things in it can be reached from the internet (load balancers)
- **Private subnet**: no direct internet route, which is where databases and app servers belong
- **NAT Gateway**: lets private things reach *out* to the internet without being reachable from it (this is the part that costs money, so we skip it)

### 5.3 Create the project

Make a new empty folder, for example `simple-vpc`, and create one file inside it called `main.tf`:

```hcl
terraform {
  required_version = ">= 1.7"

  required_providers {
    aws = {
      source  = "hashicorp/aws"
      version = "~> 5.0"
    }
  }
  # No backend block: Terraform keeps its state in a local file
  # called terraform.tfstate in this folder. Fine for solo learning.
}

provider "aws" {
  region = "eu-west-2" # change to your region
}

# ---------- The network itself ----------

resource "aws_vpc" "learning" {
  cidr_block           = "10.20.0.0/16" # ~65,000 IP addresses
  enable_dns_support   = true
  enable_dns_hostnames = true

  tags = {
    Name = "learning-vpc"
  }
}

# Lets anything in a PUBLIC subnet reach the internet directly
resource "aws_internet_gateway" "learning" {
  vpc_id = aws_vpc.learning.id

  tags = {
    Name = "learning-igw"
  }
}

# ---------- Public subnet ----------

resource "aws_subnet" "public" {
  vpc_id                  = aws_vpc.learning.id
  cidr_block              = "10.20.1.0/24" # 256 addresses
  availability_zone       = "eu-west-2a"   # must match your region
  map_public_ip_on_launch = true

  tags = {
    Name = "learning-public-subnet"
  }
}

# A route table is the set of rules for where traffic may go
resource "aws_route_table" "public" {
  vpc_id = aws_vpc.learning.id

  route {
    cidr_block = "0.0.0.0/0" # anywhere on the internet
    gateway_id = aws_internet_gateway.learning.id
  }

  tags = {
    Name = "learning-public-rt"
  }
}

# Without this association the subnet doesn't use the route table
resource "aws_route_table_association" "public" {
  subnet_id      = aws_subnet.public.id
  route_table_id = aws_route_table.public.id
}

# ---------- Private subnet (no internet route at all) ----------

resource "aws_subnet" "private" {
  vpc_id            = aws_vpc.learning.id
  cidr_block        = "10.20.2.0/24"
  availability_zone = "eu-west-2a"

  tags = {
    Name = "learning-private-subnet"
  }
}

# ---------- Outputs ----------

output "vpc_id" {
  value = aws_vpc.learning.id
}

output "public_subnet_id" {
  value = aws_subnet.public.id
}

output "private_subnet_id" {
  value = aws_subnet.private.id
}
```

Each `resource` block is documented in the [Terraform AWS provider docs](https://registry.terraform.io/providers/hashicorp/aws/latest/docs/resources/vpc.html) (look up `aws_vpc`, `aws_subnet`, `aws_internet_gateway` and `aws_route_table` there). If you want a guided version of this, HashiCorp's [AWS get started tutorial](https://developer.hashicorp.com/terraform/tutorials/aws-get-started) is a good companion.

That's six resources: the VPC, the internet gateway, two subnets, one route table and one route table association. The private subnet deliberately has no route table, which is the simplest way to see "private means no path to the internet".

### 5.4 Run it

From inside the folder:

```powershell
terraform init       # downloads the AWS provider plugin
terraform fmt        # tidies formatting
terraform validate   # checks the syntax
terraform plan       # preview: shows what WOULD be created, changes nothing
terraform apply      # creates it; type "yes" when asked
```

> **Analogy:** `terraform plan` is a **builder's written quote**: it lists exactly what they intend to build and what it will change, and nothing is built yet. `terraform apply` is you signing the quote and the work starting. You'd never sign without reading the quote first.

Read the `plan` output before applying. It lists every resource Terraform intends to create, marked with `+`. When `apply` finishes it prints your three outputs. Docs: [`terraform plan` command reference](https://developer.hashicorp.com/terraform/cli/commands/plan) and the [Terraform workflow overview](https://developer.hashicorp.com/terraform/cli/run).

### 5.5 Look inside the state file

After `apply` there's a `terraform.tfstate` file next to `main.tf`. Open it in a text editor. It's plain JSON, and you can find your VPC ID in there. That file *is* Terraform's memory: it's how Terraform knows what exists, so that running `apply` twice doesn't create everything twice.

> **Analogy:** the state file is a **stocktake sheet**. Your `.tf` files are the shopping list of what you *want*, the AWS account is what's actually on the shelves, and the state sheet records what Terraform already put there. Lose the sheet and Terraform can't tell what it already bought, so it may try to order everything again.

Docs: [Terraform state](https://developer.hashicorp.com/terraform/docs/state).

**Treat it as sensitive.** State files can contain resource IDs and, in other projects, secrets. Don't commit it to Git, and don't paste it into a blog post. A `.gitignore` for a Terraform project should include:

```
*.tfstate
*.tfstate.*
.terraform/
terraform.tfvars
crash.log
```

### 5.6 Clean up

```powershell
terraform destroy
```

Type `yes`. Everything here is free, but destroying things when you're done is a habit worth building, and it becomes essential once you add paid resources like NAT gateways or Kubernetes clusters.

## Troubleshooting: errors you may hit and how to fix them

| Where | What I saw | What it meant | Fix |
|---|---|---|---|
| Console access keys screen | "Alternatives recommended: use `aws login`" | AWS prefers short-term credentials over long-lived keys | Use `aws login` |
| `aws login` | Command not available (CLI `2.31.14`) | `aws login` needs 2.32.0 or higher | Upgrade the AWS CLI v2, then open a new terminal |
| `aws login` | `Profile 'default' is already configured with Access Key credentials.` | Old static keys in the `default` profile | Back up `%USERPROFILE%\.aws\credentials` and retry, or use `--profile` |
| Browser sign-in | `Authentication failed. Your authentication information is incorrect.` | Usually signing in on the wrong page (root page vs IAM page) | Use `https://<YOUR_ACCOUNT_ID>.signin.aws.amazon.com/console` with the IAM username, or reset the IAM password |
| Terminal | `'terraform' is not recognized as an internal or external command` | Terraform not installed or not on PATH | `winget install HashiCorp.Terraform`, or add its folder to PATH and reopen the terminal |

## Security checklist before you publish or share anything

- [ ] No account IDs, access keys, secrets or session tokens in screenshots or pasted output
- [ ] No real email addresses in budget or alert settings you show
- [ ] `terraform.tfstate`, `.terraform/` and `terraform.tfvars` are not committed to Git
- [ ] Root user has MFA, and you only use your IAM user day to day
- [ ] You destroyed (or consciously left running) everything you created
